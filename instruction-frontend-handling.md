# Care Plan Admin Frontend Handling

This guide is for **Admin Dashboard only**.

## 1) Required vs Generated Fields

### Required from frontend

- Create care plan (`POST /care-plans`)
  - `enrollment_id` (required)
  - `starts_on` (not accepted at this step)
  - `ends_on` (not accepted at this step)
- Update basics (`PATCH /care-plans/{id}/basics`)
  - `starts_on` (required)
  - `ends_on` (required)
  - If dates are changed and days already exist:
    - `draft`: backend rejects until days are regenerated with `replace_existing=true`
    - `active`: backend rejects and requires revision flow
- Generate days (`POST /care-plans/{id}/days/generate`)
  - no day count/date payload required
  - optional `replace_existing` boolean

### Generated by backend

- `care_plans.code`
- `care_plans.cycle_number`
- `care_plan_days.day_number` (1..N)
- `care_plan_days.target_date` (contiguous from `starts_on` to `ends_on`)
- status timestamps (`activated_at`, etc.)

## 2) Core Timeline Rules

- Plan dates are mandatory: `starts_on`, `ends_on`.
- `ends_on` must be `>= starts_on`.
- Days are deterministic from plan range:
  - `day_number = 1..N`
  - `target_date = starts_on + (day_number - 1)`
  - `N = diff(starts_on, ends_on) + 1`
- Frontend must not offer arbitrary day date editing or manual day date payloads.

## 3) Admin Flow (Recommended)

### Step 1: Plan Basics
- Select enrollment
- Save initial draft (only enrollment selected)
- Open basics step and set required start/end dates

### Step 2: Generate Days
- Call day generation endpoint
- Backend generates full contiguous day set from plan dates
- Use `replace_existing=true` when:
  - regenerating draft days after date changes
  - regenerating any existing draft day set

### Step 3: Day Builder
- Navigate by day tabs
- Edit section items (`nutrition`, `movement`, `activity`, `recovery`)
- Movement supports nested exercises

### Step 4: Validate & Activate
- Run validate endpoint
- Show issue list and jump links
- Activate only when valid

## 4) Status-Based Admin Behavior

### Draft
- Fully editable
- Regeneration allowed with `replace_existing=true`
- If dates are changed after days exist, backend requires regeneration before further progress.

### Active
- Keep structure stable
- No destructive replacement of day set
- For major updates, use revision flow
- Date changes on active plans with existing days are rejected; use revision.

### Completed / Cancelled
- Read-only for plan structure

## 5) APIs Admin Must Use

- `POST /api/v1/web/admin/care-plans`
- `PATCH /api/v1/web/admin/care-plans/{care_plan}/basics`
- `POST /api/v1/web/admin/care-plans/{care_plan}/days/generate`
- `GET /api/v1/web/admin/care-plans/{care_plan}/builder`
- `PUT /api/v1/web/admin/care-plans/{care_plan}/days/{day}/sections/{section}/items`
- `POST /api/v1/web/admin/care-plans/{care_plan}/validate`
- `POST /api/v1/web/admin/care-plans/{care_plan}/activate`
- `POST /api/v1/web/admin/care-plans/{care_plan}/revision`

Related lookups:
- `GET /api/v1/lookup/enrollments` (scheduled + active)
- `GET /api/v1/lookup/movement-exercises`
- `GET /api/v1/lookup/units`

## 6) Response Contract (Common Envelope)

Success:

```json
{
  "status": "success",
  "message": "Operation message",
  "data": {},
  "meta": {
    "version": "v1"
  }
}
```

Validation failure:

```json
{
  "status": "error",
  "message": "The given data was invalid.",
  "errors": {
    "field": ["Validation message"]
  },
  "meta": {
    "version": "v1"
  }
}
```

## 7) Per-Endpoint Input Contract (Admin)

### `POST /api/v1/web/admin/care-plans`
Accepted:
- `enrollment_id` (required)

Rejected/unexpected at this step:
- `starts_on`
- `ends_on`

### `PATCH /api/v1/web/admin/care-plans/{care_plan}/basics`
Accepted:
- `starts_on` (required)
- `ends_on` (required)

### `POST /api/v1/web/admin/care-plans/{care_plan}/days/generate`
Accepted:
- `replace_existing` (optional boolean)

Backend-derived:
- day count from plan range
- day numbers and target dates

## 8) Edge Cases Admin UI Must Handle

- Dates changed after days already exist:
  - prompt for regeneration (`replace_existing=true`)
  - if active, show revision CTA instead of regeneration
- Days generation requested before basics dates are set:
  - show blocking validation from backend for `starts_on`/`ends_on`
- Activation blocked by validation:
  - keep activate button disabled
  - show exact issues list
- Active plan structural conflict:
  - show revision CTA
- Stale screen data:
  - re-fetch builder payload after mutations
- Network failure:
  - keep local unsaved state and allow retry

## 9) Practical UI Checklist

- Wizard with progress indicator
- Date picker with clear min/max validation (basics step only)
- Regenerate-days confirmation modal
- Day/section editor with autosave feedback
- Validation summary panel with jump links
- Activation confirmation modal
