# Admin Period Reports — Frontend Guide (Next.js)

Guide for the Next.js admin app. Covers the period-reports table, detail view, and **PDF download button**.

---

## What this feature is

A **period report** is the client-facing care-plan report for one reporting period (`CarePlanReportRun`). Admins list them, open detail, and download a PDF.

**Important:** the PDF is generated **on the backend**. Do **not** build PDF in Next.js (no `jspdf`, `react-pdf`, html2canvas for this). Call the download API and save the file.

| Who | What they get |
|-----|----------------|
| Admin / Super Admin | List, show, download |
| Support | `403` on all three |
| Guest | `401` |

Base path (versioned API):

```text
{API_BASE}/v1/web/admin/period-reports
```

All routes require Sanctum auth (`auth:sanctum`) — same session cookie / token pattern as the rest of the admin SPA.

---

## Endpoints at a glance

| Method | Path | Response | Purpose |
|--------|------|----------|---------|
| `GET` | `/v1/web/admin/period-reports` | JSON envelope | Paginated table |
| `GET` | `/v1/web/admin/period-reports/{id}` | JSON envelope | Detail / overview |
| `GET` | `/v1/web/admin/period-reports/{id}/download` | **Raw PDF bytes** | Download button |

`{id}` is the report run id (`data[].id` from the list).

---

## Statuses & UI logic

| `status` | Meaning | `is_editable` | PDF watermark |
|----------|---------|---------------|---------------|
| `in_review` | Draft awaiting publish | `true` | `DRAFT — NOT FOR DISTRIBUTION` |
| `published` | Live for the client | `false` | none |
| `archived` | Archived | `false` | `ARCHIVED — NOT FOR DISTRIBUTION` |

**Download is allowed for all three statuses.** Do not hide the button for drafts; the PDF is stamped so it cannot be mistaken for the client’s published copy.

**List default filter:** if you omit `status`, the API returns only `in_review` + `published` (archived is excluded unless you pass `status=archived`).

## 1. List — period reports table

```http
GET /v1/web/admin/period-reports
```

### Query params

| Param | Type | Rules | Notes |
|-------|------|-------|-------|
| `status` | string | `in_review` \| `published` \| `archived` | Optional |
| `search` | string | max 100 | Matches report `code`, care plan `code`, client name / email / `client_code` |
| `care_plan_id` | integer | must exist | Optional |
| `per_page` | integer | 1–100 | Default `15` |

### Success response (standard envelope)

```json
{
  "status": "success",
  "message": "Client period reports retrieved successfully.",
  "data": [ /* rows */ ],
  "meta": {
    "version": "v1",
    "pagination": {
      "current_page": 1,
      "per_page": 15,
      "total": 42,
      "last_page": 3,
      "from": 1,
      "to": 15,
      "has_more_pages": true,
      "path": "...",
      "next_page_url": "...",
      "prev_page_url": null
    }
  }
}
```

### Row shape (`data[]`)

```ts
type PeriodReportListRow = {
  id: number;
  code: string;                    // e.g. "RPT-000148"
  status: "in_review" | "published" | "archived";

  adherence_percentage: number;    // 0–100, scheduled tasks logged in period
  period: {
    starts_on: string | null;      // "YYYY-MM-DD"
    ends_on: string | null;

  operational_log: { id: number; code: string } | null;
  care_plan: {
    id: number;
    code: string;
    status: string;
    starts_on: string | null;
    ends_on: string | null;
  } | null;
  client: {
    id: number;
    name: string;
    client_code: string | null;
    email: string;
    picture_url: string | null;
  } | null;
  generated_by: { id: number; name: string } | null;
  timestamps: {
    submitted_for_review_at: string | null; // ISO 8601
    published_at: string | null;
    locked_at: string | null;
    created_at: string | null;
    updated_at: string | null;
  };
};
```

### Suggested table columns

- Client (avatar + name + `client_code`)
- Report code
- Care plan code
- Period (`starts_on` → `ends_on`)
- Adherence (`adherence_percentage` + `%`)
- Status badge
- Generated by
- Updated / published date
- Actions: **View**, **Download**, Edit (only if `is_editable`)

Use `row.id` for show + download URLs.

## 2. Show — detail / overview

```http
GET /v1/web/admin/period-reports/{id}
```

Same auth as list. Returns the full client-facing overview (metrics, daily points, highlights, feedback, care plan / client context).

Useful for a detail page or drawer. Download does **not** need this payload — the PDF is built entirely on the server from the report id.

## 3. Download — PDF file

```http
GET /v1/web/admin/period-reports/{id}/download
```

### What you get

| Header | Value |
|--------|--------|
| `Content-Type` | `application/pdf` |
| `Content-Disposition` | `attachment; filename="period-report-{code}-{start}-to-{end}.pdf"` |
| `Cache-Control` | `private, no-store` |
| Body | Raw PDF bytes (not JSON) |

Example filename:

```text
period-report-rpt-000148-2026-06-01-to-2026-06-14.pdf
```

### Special middleware note

Most admin API routes require `Accept: application/json` and return `406` otherwise.

**This download route is exempt** so a browser can open it as a file download. Prefer `fetch` + blob (below) so you can show a spinner and handle `401` / `403` / `404` / `500` cleanly.

### Recommended Next.js pattern

```ts
async function downloadPeriodReportPdf(reportId: number) {
  const res = await fetch(
    `${process.env.NEXT_PUBLIC_API_URL}/v1/web/admin/period-reports/${reportId}/download`,
    {
      method: "GET",
      credentials: "include", // Sanctum SPA cookie session
      // Optional: helps error responses stay JSON when the API error handler kicks in
      headers: { Accept: "application/json" },
    },
  );

  if (!res.ok) {
    // On failure you may get JSON: { status: "error", message: "..." }
    let message = "Failed to download period report.";
    try {
      const err = await res.json();
      message = err.message ?? message;
    } catch {
      // non-JSON error body
    }
    throw new Error(message);
  }

  const blob = await res.blob();

  // Prefer server filename when present
  const disposition = res.headers.get("Content-Disposition") ?? "";
  const match = /filename="([^"]+)"/.exec(disposition);
  const filename = match?.[1] ?? `period-report-${reportId}.pdf`;

  const url = URL.createObjectURL(blob);
  const a = document.createElement("a");
  a.href = url;
  a.download = filename;
  document.body.appendChild(a);
  a.click();
  a.remove();
  URL.revokeObjectURL(url);
}
```

### UX tips

1. Disable the button / show a spinner while the request is in flight (PDF can take ~0.5–2s).
2. Toast on success / failure.
3. Show download for **every** status; optionally hint drafts are watermarked (e.g. tooltip: “Draft PDF includes a watermark”).
4. Do **not** open the URL in a new tab with `window.open` unless cookies are correctly shared — `fetch` + blob is safer with Sanctum SPA auth.

### Alternative: plain link

Because the route skips the JSON-only guard, this also works if the admin session cookie is sent:

```tsx
<a href={`${API}/v1/web/admin/period-reports/${id}/download`}>Download</a>
```

You lose loading state and structured error handling — use only if that is acceptable.

## What is inside the PDF

Matches the **client-facing** report (same idea as the mobile app), not the full internal admin workspace.

Includes:

- Report code, status label, period dates, adherence
- Client name / code / email
- Care plan code, program title, plan date range
- **Visible** highlight cards only (`is_visible_to_client = true`)
- Metric sections linked to those highlights (with daily bar charts when data exists)
- Care-team feedback: `summary` + `focus_next_period` (not internal `notes`)
- Footer: report code · client name · generated timestamp

Does **not** include:

- Hidden highlights
- Operational metrics not tied to a visible highlight
- Internal workspace evidence / raw day logs
- Internal feedback `notes`

Empty cases still download a valid PDF (placeholders / empty-state copy for missing highlights, metrics, or feedback).

## Errors frontend should handle

| HTTP | When | Typical handling |
|------|------|------------------|
| `401` | Not logged in | Redirect to login |
| `403` | Support (or unauthorized role) | Hide table / show “no access” |
| `404` | Unknown `id` | Toast “Report not found” |
| `422` | Invalid list query params | Show field errors from `errors` |
| `406` | Non-JSON Accept on **list/show** (not download) | Always send `Accept: application/json` for JSON APIs |
| `500` | PDF engine failure | Toast “Could not generate PDF. Try again.” |

JSON error envelope (when applicable):

```json
{
  "status": "error",
  "message": "Human-readable message.",
  "errors": {},
  "meta": { "version": "v1" }
}
```

## Auth checklist

- Same Sanctum SPA setup as other admin pages (`credentials: "include"`, CSRF if you already use it for mutations).
- Roles: **admin** and **super_admin** only for care-plan / period-report screens.
- Support users should not see a working download button (or the whole page).

## Frontend responsibilities (summary)

| Do | Don’t |
|----|--------|
| Call list / show / download APIs | Generate PDF in the browser |
| Wire Download on every row (all statuses) | Restrict download to `published` only |
| Use `id` from the list for download | Invent filename or report content client-side |
| Parse `Content-Disposition` for filename | Assume a fixed filename |
| Show loading + errors on download | Silent `window.open` without feedback |
| Treat list default as non-archived | Assume archived rows appear without `status=archived` |
